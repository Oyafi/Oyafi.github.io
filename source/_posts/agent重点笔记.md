## 一、上下文优化

### 1.静态信息放入system prompt，动态信息采用追加模式

在llm推理的过程中，每次当前token的value计算都依赖与之前所有token的k,v。因此在前缀不变的情况下，大部分的推理引擎都引入了kvcache的机制，也就是缓存之前推理的前缀token kv。对于多次请求，推理框架会提取当前prompt和之前prompt的前缀，将kv填充到kvcache中，从而跳过之前到计算，被称之为prefix cache，因此，如果能够保持上下文前缀尽可能长，就能够很好的利用到kv cache，极大的加快模型的推理速度，减少推理成本。

举个例子，如果你需要告知模型当前的系统时间，这个动态的系统时间不应该放在提示词最开始的位置，而应该放在最后的位置。

### 2.一些常见的有害上下文管理

1. 动态前缀，如系统提示词中插入时间，次数等信息
2. 工具定义动态排序
3. 滑动窗口控制历史消息
4. 采用非标准消息格式

### 3. 缓存对架构的约束

1. 可变内容应放到缓存边界之后
2. 子agent应与父agent字节级对齐
3. 工具调用摘要后，摘要本身也有必要持久化，而不是只持久化工具调用本体。

### 4.提示词优化技巧

1. 使用一定的语气，如must，使用大写字母等
2. 使用结构化的输入，如xml，md
3. 比起给出一大堆规则，最好给出完整的状态机流程
4. 规则细化，尽可能减少二义性
5. 可以给出示例，但是注意场景，如果规则清晰则没必要，否则会稀释注意力

### 5.防止提示词注入

1. 使用标签包裹后再注入上下文，如<external_content>
2. 利用结构化角色机制，不要将用户内容放入system
3. 在prompt中提示
4. 外部过滤，如关键词屏蔽

实验结果, 混合使用效果最佳

## 二、工具

### 1.专用工具还是skill + 通用工具

1. 参数复杂度，参数复杂时专用的schema校验能够很好的增加工具的可靠性，参数简单时，使用cli相信模型的自动填充就够了
2. 变更频率，改文档比改代码简单，不变的底层工具使用专用，快速变化的使用skill
3. 模型能力，能力较强时可信任skill，能力较弱时推荐专用tool更可靠

### 2.MCP安全保障

1. 接入前审查description
2. 服务器版本锁定，拒绝静默更新
3. 最小权限原则

### 3.工具执行安全

1. 输入验证，过滤场景注入，比如路径遍历问题，参数注入问题
2. 权限管理
3. 引入轻量模型，sidecar并行审查







面向常驻型智能助手设计的 Agent 运行时，覆盖模型调用、工具调度、上下文治理、多 Agent 协作和消息投递

- 设计统一消息架构，支持 QQ、Telegram和 自定义WebSocket 接入，实现平台协议与 Agent 逻辑解耦；新平台可通过适配器快速扩展，并支持会话恢复和消息可靠投递。
- 基于 LiteLLM 统一不同模型厂商接口，屏蔽请求、流式响应和工具调用协议差异；对认证、限流、连接及超时错误分类处理，为可恢复异常提供指数退避重试，加入流式看门狗机制。
- 构建声明式工具抽象，通过 `BuildTool` 统一 Schema、执行器及运行策略；调度器根据工具级并发谓词生成批次化执行计划，以串行屏障隔离有副作用的调用，并对存在前后依赖的 Bash 命令执行失败传播。采用延迟 Schema 暴露机制，低频工具仅在模型检索命中后加入上下文。
- 设计分层 Prompt 编排机制，将跨 Agent 复用的安全约束作为稳定前缀，Agent 身份、SOUL 和工作区配置组成静态上下文，时间及消息平台等请求级信息置于动态尾部，提升 Prompt 前缀稳定性与缓存复用率
- 设计分层上下文治理机制，对超长工具结果执行落盘与引用回填，并按结果体积控制单轮聚合规模；当上下文窗口使用率达到 80% 时生成 compact 检查点，以追加式 JSONL 保留完整历史，仅向模型注入摘要和近期消息。
