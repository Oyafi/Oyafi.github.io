# HTTP、SSE 与 WebSocket：通信模型、连接复用与协议开销

在实时通信场景中，HTTP、SSE 和 WebSocket 经常被放在一起比较。但三者并不是完全并列的协议：

- HTTP提供请求与响应模型；
- SSE是在HTTP响应上定义的服务器事件流；
- WebSocket通过HTTP握手建立独立的全双工通信通道。

理解它们的关键，不只是比较“是否长连接”，还要区分底层连接、逻辑数据流和应用层通信语义。

## 一、普通HTTP

普通HTTP通常遵循：

```
客户端发送请求
→ 服务器处理请求
→ 返回响应
→ 本次逻辑交互结束
```

例如：

```
POST /api/orders HTTP/1.1
Content-Type: application/json

{"productId":1001}
```

每个请求都是一个相对独立的逻辑事务，包含：

- 请求方法；
- URL；
- 请求头；
  -认证信息；
- 请求体；
- 响应状态码；
- 响应头和响应体。

HTTP非常适合查询、提交订单、修改资料等低频、独立的业务操作。

## 二、SSE

SSE全称为 Server-Sent Events，是建立在HTTP之上的服务器单向推送机制。

客户端发送一次请求：

```
GET /api/events HTTP/1.1
Accept: text/event-stream
```

服务器不立即结束响应，而是不断写入事件：

```
event: order-status
id: 1001
data: {"status":"PAID"}

event: order-status
id: 1002
data: {"status":"SHIPPED"}
```

事件之间使用空行分隔。空行只表示一条事件结束，并不表示连接关闭。

SSE连接会持续存在，直到：

- 服务器结束响应；
- 客户端调用 `EventSource.close()`；
- 页面关闭；
- 网络断开；
- 代理或服务器超时。

浏览器的 `EventSource` 还原生支持自动重连和 `Last-Event-ID`。

## 三、SSE为什么是单向的

SSE的通信过程是：

```
客户端发送GET请求
→ 请求已经结束
→ 服务器持续写HTTP响应体
```

客户端不能继续向已经发送结束的GET请求体追加数据。因此，SSE的逻辑方向是：

```
服务器 → 客户端
```

客户端需要发送数据时，必须创建新的HTTP请求：

```
客户端 → POST请求 → 服务器
服务器 → SSE事件 → 客户端
```

这种组合非常适合大模型对话：

```
POST发送问题
SSE流式返回Token
```

## 四、POST能否复用SSE的连接

需要区分：

```
底层TCP连接
与
逻辑HTTP Stream
```

### HTTP/1.1

SSE响应长期不结束。一条HTTP/1.1连接通常无法在前一个响应未结束时正常处理后续独立请求，因此浏览器一般使用两条连接：

```
TCP连接1：SSE持续响应
TCP连接2：POST普通请求
```

### HTTP/2

HTTP/2支持多路复用：

```
一条TCP连接
├── Stream 1：SSE
├── Stream 3：POST /message
├── Stream 5：GET /user
└── Stream 7：其他请求
```

因此POST和SSE可以复用同一条底层TCP连接，但仍然是两个独立的HTTP Stream，不能直接向SSE的GET请求中写入客户端消息。

HTTP/3同样支持多路逻辑流，只是底层使用QUIC。

## 五、为什么还需要WebSocket

WebSocket解决的主要问题不是“减少一条TCP连接”，而是提供：

```
同一个逻辑通道上的全双工通信
```

建立连接后：

```
客户端 ⇄ WebSocket ⇄ 服务器
```

双方随时都可以发送消息，不再受到HTTP请求响应模型的限制。

它适合：

- 即时聊天；
- 实时游戏；
- 协同编辑；
- 在线状态和输入状态；
- 高频设备控制；
- 二进制实时数据。

SSE更适合：

- 大模型文本流；
- 任务进度；
- 后台日志；
- 订单状态；
- 系统通知；
- 行情推送。

## 六、重复POST的问题是什么

重复发送POST不一定不好。低频业务操作使用POST通常更简单、更容易鉴权和追踪。

它在高频实时通信中的问题，不只是请求头产生了额外字节，更根本的是通信模型不匹配。

每个POST都需要经历：

```
创建HTTP Stream
→ 编码请求头
→ 路由匹配
→ 鉴权和过滤
→ 解析参数
→ 创建请求上下文
→ 处理业务
→ 生成响应
→ 结束当前Stream
```

这些开销包括：

1. 传输开销：方法、URL、Cookie、认证头和响应头；
2. 计算开销：路由、鉴权、解析、日志和对象创建；
3. 语义开销：维护多个请求之间的顺序、会话和状态。

HTTP/2通过连接复用和头部压缩减少了传输成本，但每个POST仍然是一个独立请求。

WebSocket只在握手时使用HTTP，后续直接交换轻量消息帧，更适合大量、高频、小尺寸消息。

## 七、WebSocket不是纯业务数据

WebSocket建立连接后，每条消息仍然包含帧头。

基础帧头包含：

```
FIN
RSV
Opcode
MASK
Payload Length
```

常见Opcode包括：

| Opcode | 含义       |
| ------ | ---------- |
| `0x1`  | 文本数据   |
| `0x2`  | 二进制数据 |
| `0x8`  | 关闭       |
| `0x9`  | Ping       |
| `0xA`  | Pong       |

根据Payload长度，WebSocket协议开销为：

| Payload长度    | 服务端到客户端 | 客户端到服务端 |
| -------------- | -------------- | -------------- |
| 0～125字节     | 2字节          | 6字节          |
| 126～65535字节 | 4字节          | 8字节          |
| 超过65535字节  | 10字节         | 14字节         |

客户端向服务器发送时额外增加4字节Mask Key。Mask用于协议安全处理，不是加密；真正的加密由 `wss://` 和TLS提供。

例如客户端发送5字节的 `hello`：

```
2字节基础帧头
+ 4字节Mask Key
+ 5字节Payload
= 11字节
```

## 八、应用层格式仍然存在开销

WebSocket只规定消息如何封装，不规定业务内容格式。

如果发送JSON：

```
{
  "type": "chat",
  "userId": 1001,
  "content": "hello"
}
```

字段名、引号和括号都是应用协议的一部分。

完整数据链路为：

```
WebSocket帧头
+ JSON/Protobuf等业务协议
+ 真正业务数据
+ TLS
+ TCP
+ IP
```

如果数据量大且频率高，可以使用Protobuf等二进制协议减少业务层编码开销。

## 九、WebSocket为什么不能完全替代HTTP和SSE

WebSocket能力更强，但需要业务自己处理：

- 断线重连；
- 心跳；
- 消息确认；
- 消息顺序；
- 断线补发；
- 用户和连接绑定；
- 多实例消息转发；
- 网关和负载均衡配置。

SSE已经基于HTTP提供事件格式、自动重连和较好的基础设施兼容性。只需要服务器单向推送时，没有必要为了全双工能力引入WebSocket的额外复杂度。

## 十、技术选择

| 场景                           | 推荐方式        |
| ------------------------------ | --------------- |
| 普通查询和数据提交             | HTTP            |
| 客户端偶尔请求、服务器持续推送 | HTTP POST + SSE |
| 大模型逐字输出                 | SSE             |
| 任务进度和系统通知             | SSE             |
| 即时聊天和在线状态             | WebSocket       |
| 实时游戏和协同编辑             | WebSocket       |
| 高频双向小消息                 | WebSocket       |
| 二进制实时通信                 | WebSocket       |

## 面试总结

> SSE是基于HTTP的服务器单向事件流，一条事件结束不会关闭连接。客户端需要发送数据时，可以通过新的POST请求完成；在HTTP/2下，POST和SSE可以复用同一条底层TCP连接，但仍然属于不同的HTTP Stream。WebSocket则提供同一个逻辑连接上的全双工通信。它的优势不只是帧头更小，还在于避免为每条消息重复创建完整的HTTP请求语义，因此更适合高频双向通信。普通请求响应使用HTTP，服务器单向持续推送使用SSE，高频双向或二进制通信使用WebSocket。
